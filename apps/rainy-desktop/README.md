# RainyAgent desktop

English | [中文](README.zh.md)

RainyAgent is a Windows x64 Electron carrier whose core installer includes the Windows Host, bundled Strata engine and Python runtime, and a WSL2 Host payload. Model weights remain user-supplied. It preserves the upstream Agent loop, session persistence and Web chat with four default tools: `read`, `write`, `edit`, and the selected platform shell (`pwsh` or `bash`). The upstream baseline is version 0.1.7-rc.2.

The [Chinese installation and configuration guide](README.zh-CN.md) owns the product workflow, configuration reference and source build instructions. [Validation](VALIDATION.md) distinguishes simulated providers from real API runs and records unresolved acceptance items. [Attribution](THIRD_PARTY_NOTICES.md) describes the upstream and packaged dependencies.

## Offline installation and recovery

The [1.0.2 release](https://github.com/RainyMarks/RainyAgent/releases/tag/v1.0.2) provides the core installer. Updated native-tool volumes are in the [1.0.2 resource archive](https://github.com/RainyMarks/RainyAgent/releases/tag/v1.0.2-resources); unchanged `environment/` WSL installation media and `environment-components/` runtime archives remain in the [1.0.0 resource archive](https://github.com/RainyMarks/RainyAgent/releases/tag/v1.0.0-resources). The core starts natively on Windows without WSL or scientific libraries. Source packaging restores pinned inputs from both archives under `release/offline-1.0.2`. Native tools are optional: online installation uses the catalog, while matching adjacent volumes also work with the installer. Each native-tool volume is limited to 2 GiB.

The tool installation window reports the current stage, file and stage progress. Cancel requests a safe stop and waits for any required rollback. Re-running the same complete release rechecks the volumes and can reuse verified staging files. Missing or corrupt volumes and insufficient space stop installation before tool replacement. Before updating, save your work and close RainyAgent, native tools and their command windows; the installer reports occupied tools instead of terminating them.

Third-party Electron ASAR archives are installed, verified and backed up as complete binary files. Catalog probes and offline HTTP responses read these payloads through the unmodified disk filesystem. The carrier's own packaged pages retain normal ASAR loading and integrity protection. [The real Electron fixture](tests/toolpack-electron.mjs) checks installation, cancellation, retry, user-file preservation, catalog inspection and raw archive serving in a private temporary directory.

Upgrades preserve declared settings and user-added files in retained tool directories. A saved inventory for each installed package distinguishes program files from user files; obsolete program files are removed. When a package omits a previously inventoried tool, the upgrade moves that tool's complete directory and user data to `.rainy-toolpack/backups/<transactionId>/` for manual recovery. Directories outside the previous inventory remain untouched. A conflicting user path or missing prior inventory stops the upgrade before replacement and identifies the affected path. Recovery records, package inventories and old tool directories remain under `.rainy-toolpack`. Uninstalling the application preserves `tools/`, `runtime/`, recovery records and user data.

New installations start on Windows; existing saved WSL choices are retained. Runtime settings list registered WSL2 distributions and can prepare an application-owned Ubuntu 26.04.1 environment from the external offline media. Creating WSL system components remains an explicit action, with administrator approval and a restart when Windows requires it. Existing distributions and their data are preserved. A missing saved distribution opens recovery instead of silently choosing another target. Clean-Windows administrator approval and restart recovery remain separate acceptance items.

## Application updates

The packaged app checks stable releases from `RainyMarks/RainyAgent` on GitHub at startup and downloads an available core update in the background. Help → Check for updates provides manual status and retry. A prepared update offers Later or Restart and install; installation starts only after confirmation, draft saving, and Host cleanup. A failed save keeps the app open. Ordinary exit does not install a downloaded update, and the updater does not select prereleases or downgrade the installed version.

Automatic updates replace the core application and preserve installed optional tools and environments. They do not download native-tool volumes, WSL media, or CPU/CUDA environment components again. Optional component installation and repair continue to use matching offline release files. [Validation](VALIDATION.md) records the update checks completed for the published artifacts.

## Runtime contract

The explicit `cordis.patch.yml` profile excludes official accounts, telemetry, office runtimes, browser/computer control, schedules, multi-agent tools and the plugin marketplace. One selected Windows or WSL Host owns commands, terminals, model connections and sessions. The Windows carrier owns the window, native tool windows and shared project catalog. Lifecycle control uses stdin/stdout; authenticated HTTP/WebSocket carries application data. Target switching saves drafts and refuses running or queued Agent work, programs, debugging and terminals. New execution is frozen before the target preference changes.

WSL startup waits for Windows-side loopback TCP reachability after the Host reports profile readiness. Connection refusal is retried within the original 90-second startup deadline; other connection errors fail startup. This check sends no HTTP request or authentication token. Cancellation, timeout and Host exit stop probing, and transport shutdown waits for the owned socket and child process to close. Native Windows startup has no cross-OS probe.

Native window controls share the single top toolbar. Empty header space supports dragging and double-click maximization; editing and zoom shortcuts remain available. Unified settings separate models, context, project memory, skills, MCP and runtime controls. Runtime settings select the execution target, inspect existing interpreters and import release-approved offline components.

New workspaces show files on the left and the main editor. Top-toolbar buttons reveal AI conversations and the bottom panel when needed; View → Focus editor hides both. Existing workspaces retain their saved pane visibility and widths. File actions occupy one row, editor actions share the open-tab row, and CTF tools open as a closable tab. Tight windows can show files over the editor. Editor tabs, conversations and the retained CTF workbench keep separate state. The homepage and About credit read `Develop by NCUCyberBase`. Active reasoning displays “Thinking...” in English and “思考中” in Chinese; the elapsed-time control uses the corresponding localized text.

## Code workspace

A project starts from the folder explicitly opened by the user; a fresh installation does not create a desktop project. Add Folder attaches another root with its own stable identity, and cross-root file operations remain scoped by that identity. Windows projects use native paths; WSL projects use paths mapped and canonicalized inside the selected distribution. Existing workspaces retain their identity, editor recovery and source-target chats. Switching a project binds its public identity to the destination, restores directory mounts and selects that workspace before the Host is ready, while old chats and editor recovery remain in their original Host.

Monaco provides multiple file tabs, syntax highlighting, search and replacement, undo, explicit saves and differences. File operations preserve UTF-8 BOM and line endings. Binary, non-UTF-8 and over-limit documents are read-only; the default editable limit is 5 MiB. Oversized UTF-8 previews retain up to 64 KiB without splitting a character; binary previews show up to 4 KiB as hexadecimal. Quick Open searches workspace paths with a bounded result list and reports truncation. Changing the query, switching projects, or reopening Quick Open invalidates earlier results; pending or failed searches cannot open an old result.

The editor's in-memory directory tree resolves parents from URI path segments, including Windows drive roots and UNC shares, while preserving Host paths and file URI semantics for language services. Registration, model creation and readback share Monaco's canonical URI identity. `node apps/rainy-desktop/tests/editor-files-browser.mjs` checks the real file provider in a Windows browser context, including Unicode and space paths, independent same-named files, and POSIX paths.

Recovery storage keeps dirty buffers, open tabs and pane geometry under each workspace. An external edit refreshes a clean buffer; a dirty buffer retains its text and offers a comparison. Version conflicts stop saving until the user resolves the displayed difference. Run and debug save every changed file in the current workspace and stop when a save fails.

Persistent language servers analyze unsaved editor documents: Pyright for Python, TypeScript Language Server for JavaScript/TypeScript, and clangd for C/C++. Formatting uses the bundled Ruff and Prettier, or the prepared clang-format. Python interpreter choices and CMake compilation databases also configure editor language services. Selected code is sent through a normal recorded user message containing its path, range and text.

Run configurations retain the entry, arguments, interpreter or compiler, working directory and CMake choices per workspace. Python supports files, modules and existing virtual environments; JavaScript and TypeScript use Node; PHP supports direct script runs; C/C++ supports single-file and CMake builds. Failed builds stop launch. Debugging uses debugpy, js-debug, CodeLLDB on Windows and GDB DAP on Linux for workspace-launched programs. The interface exposes breakpoints, stepping, stacks, variables, watches and stop. External process attachment and PHP debugging are unavailable.

Runtime discovery inspects project virtual environments, Conda registrations, common Python locations, PATH and imported components without installing packages into them. A selected interpreter configures project tools, terminals, runs and language services through a process-local environment. Executable readiness and library capabilities are reported separately; a working Python can lack PyTorch or CUDA. Interpreters from the other execution platform are rejected.

Offline components provide isolated Python 3.12, Node 24, Windows PHP, native C/C++ tools, and separate CPU or CUDA scientific environments. Scientific components include NumPy, SciPy, pandas, scikit-learn, image processing, Jupyter and common deep-learning libraries, with matched PyTorch 2.11, torchvision 0.26 and torchaudio 2.11. Import verifies the release catalog, archive and file inventory before selecting a content-addressed generation. Existing user environments and global PATH are unchanged. CUDA needs a compatible NVIDIA driver. The Ubuntu 26.04 amd64 development wizard installs its verified C/C++, GDB, CMake, clangd and PHP packages with downloads disabled.

## CTF workbench

Tool publishers upload verified archive pieces to a versioned resources release, then run `scripts/sign-tool-channel.mjs` with the prepared source, metadata and catalog, the release version, and a higher `--revision`. Commit its public output as `toolpacks/native-tools-channel.signed.json`. Use the tool publisher identity matching `resources/native-tools-public-keys.json`; application rebuilds can retain those public keys without owning the tool signing key. Clients do not accept new trust keys from the channel. Revisions with no tool-pack identity change do not prompt another download.

While online, select Common tools → Download all tools. Every transport piece and archive volume is checked before installing into per-user application data. Downloads support cancellation, Range resume and retry; installed tools remain available offline across restarts and application updates. First visiting the catalog checks the signed tool channel; Check tool updates repeats the check. Added or updated tools are offered for explicit download while the installed catalog remains usable. The application rejects invalid signatures, mismatched catalogs and channel revisions older than its saved revision.

The CTF entry works before a conversation is selected. Its default Common tools tab searches names and uses, filters categories, and shows favorites, recent launch requests, versions and availability. Favorites and recent entries belong to the Windows user and are shared across conversations. Saved Burp favorites migrate to Yakit; old Burp recent-launch entries are removed without recording a Yakit launch. The tool-package catalog contains these 38 entries:

Desktop programs open independently, command-line tools use prepared Windows terminals, and offline web tools use isolated windows without the native launch bridge. The success message says “Launch request sent for {name}”; it confirms platform acceptance of the request. File availability, interface readiness and functional acceptance are separate observations. `status: ready` means required files and dependencies exist; the separate `verified` flag reflects recorded acceptance for the matching catalog. Unverified tools stay labeled Not verified, and missing dependencies disable launch. The directory does not add Agent tools or prompts.

Yakit 1.4.8-0919 includes the official Yak engine 1.4.8-beta19 in `bins/yak.zip` for its built-in engine restoration. The package requires no separate engine download. Yakit follows its configured `YAKIT_HOME`; its Windows default is `yakit-projects` beside `Yakit.exe`. The package retains Yakit's [AGPLv3 license](https://github.com/yaklang/yakit/blob/v1.4.8-0919/LICENSE.md) and upstream notices. ImHex remains available in Reverse for binary editing.

IDA carries private Python 3.12.14, matching SIP bindings and the `imp` compatibility module. RainyAgent starts it with a private `IDAUSR` directory under application data and removes inherited Python and Qt overrides. The bundled Java 21.0.12.1 runtime starts StegSolve and JADX; dnSpy 6.6.0 carries .NET Desktop 10.0.9. The native-tool launcher searches packaged binaries and Windows system utilities, not a third-party system PATH. Windows still supplies its normal operating-system DLLs and device drivers.

The Windows multimon-ng build reads 16-bit mono raw audio. Its own directory includes SoX for other formats. From a directory containing `sample.wav`, run `sox.exe -R -t wav sample.wav -esigned-integer -b 16 -r 22050 -t raw sample.raw`, then `multimon-ng.exe -a DTMF -t raw sample.raw`. The tool card opens a terminal with its help text; it does not start microphone capture.

Missing-tool cards and directory-read errors offer Repair tool pack. This control expands offline repair instructions: save your work and exit RainyAgent and all tool windows, place the matching setup EXE and every tool-pack volume in the same directory, then run the installer again. After installation, reopen RainyAgent and refresh the tool status. The control only displays instructions; it does not start the installer.

The IceSky tab opens the pinned browser workbench. One retained iframe provides its existing 22 manual tools, with templates and tool components loaded on first selection. Switching back to the directory keeps that iframe. Each conversation has an independent draft; opening IceSky without a conversation or from a blank New Session page uses a separate standalone draft. The workbench follows the application's theme and font sizes. Navigation and status controls follow the application language; bundled tool prose retains its original language.

The selected Host's durable storage retains editable text, options, text results and file metadata. Drafts do not restore file contents or generated binary artifacts; after a restart, select local files again when the restored draft requests them. Drafts exclude API credentials. AI requests use a bounded, authenticated relay to the endpoint configured inside IceSky, including localhost in the selected target; the relay does not persist request keys or bodies.

Text transformations, decoding and tokenization run in cancellable workers. Automatic calculation waits 160 ms after input changes and accepts at most 64 KiB of UTF-8 input; larger inputs require the Calculate button. Token results render 100 items per page. Tool loading, computation and draft-save failures keep the current draft available for retry or export. Conversation changes, workbench refresh, native menu or keyboard reload and application exit wait for pending draft saves; a failed reload or exit save keeps the window open.

## Strata local inference

The core EXE includes Niko1221/Strata 0.1.39, Python 3.12.14, and the required server, preparation, and CUDA runtime dependencies. Users do not need a separate Strata or Python installation. The inference engine targets Windows x64 and NVIDIA CUDA 13 with driver 580 or newer; the supplied engine includes `sm75`, `sm86`, `sm89`, and `sm120` targets. This package provides no AMD or Linux inference engine. The [runtime source manifest](toolpacks/strata-runtime.sources.json) pins its inputs and licenses.

Users supply a supported Qwen3.8 Flash Next main GGUF with all shards, plus its matching MTP GGUF or prepared MTP directory. No main/MTP weights or derived dense/expert files are distributed with the runtime. In Models and context → Strata local model, choose the main source, MTP source or compatible profile, then save. An empty MTP path asks the manager to detect matching files beside the main model; API serving still requires MTP. An explicit Start prepares required model files locally before loading the server, without downloading weights. Preparation and startup can be cancelled.

The card controls the engine context window, loopback port, KV cache, reserved VRAM and resident RAM budget. Settings are stored privately under the carrier's application data directory, at `strata/settings.json`; selected model files remain outside the install directory. Only processes started by this manager can be stopped. An existing external server is identified separately and is not terminated by the card. Request reasoning and output limits remain in the ordinary model configuration.

Connect and use by default asks the selected Host to verify the actual loaded model and context before saving the local endpoint. Strata runs on Windows even when the project Host is WSL. If WSL NAT prevents access to Windows loopback, select the Windows execution target for Strata; the application does not rewrite network settings or substitute a cloud model.

Current Strata validation covers relocation of the bundled runtime, Python imports, and health/chat integration with a mock server. It does not yet establish real GPU inference, throughput, or compatibility across hardware. [Validation](VALIDATION.md) owns the tested artifact and remaining acceptance items.

## Model experience

The policy plugin admits the final counted request, serializes requests to each configured endpoint, limits retained tool output, and initiates balanced compaction. Exact full-request tokenizers are optional; fallback estimates include multilingual content and tool schemas and remain visibly marked as estimates. Explicit output limits, including the official DeepSeek maximum preset, take precedence over local defaults. All compaction inputs and outputs use DSH's durable auxiliary-call/checkpoint transactions. Automatic compaction prices and sends the complete auxiliary request with retained direct-user messages as exact reference. Its budget-specific directive summarizes verified progress, errors, unresolved work and the next action without rewriting user goals or constraints; the reference messages remain outside the replacement span. It retains the newest balanced tool pair; its recent-history target can shrink when a small window cannot fit that target. Direct user messages from the latest admitted turn remain verbatim at their current surface positions, including inputs supplied during that turn; the retained turn changes only when a new turn admits its first user message. Earlier turns remain eligible for summarization, and already shadowed messages are not restored. Automatic, idle manual, and explicit-range compaction preserve those current-turn messages; oversized protected input fails with a diagnostic. A candidate must fit the full summary input and be larger than the reserved framed checkpoint. Summary failure preserves history; overflow permits one compressed retry. An explicit thinking-off selection sends the selected protocol's disable value; leaving thinking unspecified retains provider-default behavior.

Model settings live in the selected Host's Rainy profile; credentials use its separate private credential store. Before the Host becomes ready, it repairs older Rainy-managed profiles whose explicit thinking-off setting lacked a protocol mapping, preserving addresses, budgets, credential references and other settings. Model requests use the bundled Strata server or an endpoint configured by the user. New API models default to OpenAI Responses and local models to Chat Completions; the [settings defaults](../../packages/client/ui-rainy/README.md#use-this-package) remain editable to match the service. The DeepSeek preset uses 1,000,000 context tokens. Model discovery requires only a provider, Base URL, protocol and optional request key; it does not require a model ID or context allocation and does not save the configuration. Saving and the separate streaming/tool-call diagnostic require the complete model configuration. It never silently substitutes a cloud provider. Skills and allowlisted MCP tools are selected and persisted per session; only selected registrations and bounded Skill descriptions become model-visible. The existing file reader loads a selected Skill body when needed; extension instructions and schemas must fit both the configured limit and 20% of the model input budget.

The coding prompt is concise; the default schemas preserve cancellation, filesystem observation checks and atomic writes. Searches use the selected platform shell and bundled ripgrep. Oversized text from other tools is stored on disk with a bounded view and retrieval location. The read tool owns its line windows and is exempt from secondary spilling, including when it reads a spill file. Its defaults are 2,000 lines, 2,000 characters per line and 50 KiB of selected line text; wrappers are additional. The complete model request still passes input admission, so an oversized read page is refused before provider dispatch rather than forced into a small context. A long-line truncation marker is explicit and the original file remains intact; offset and limit page lines, not columns. Session titles use the first user message without auxiliary inference. Project instructions and user messages are never silently truncated to force admission. Rainy refuses source files or instruction batches exceeding 64 KiB, identifies the files, and retries corrected dynamic instructions before the next request. Context settings report estimated system, schema, instruction, memory, extension, history and framing components separately. First-send previews read the current project and saved model without creating a chat or calling inference; pending attachments and final request-time changes remain outside that estimate. A configured tokenizer receives the selected provider/model with `system/messages/tools` and must return matching `model`, nonempty `chatTemplate`, and integer `tokens` before its count is labeled exact.

## Project memory

Project memory uses the carrier project identity across execution targets. Windows and WSL share the project record; environment-specific notes retain their target scope. Use and automatic generation have independent switches. Human edits require the displayed revision, and generated updates cannot replace or remove a manually corrected note. Deletion retains source watermarks and exclusion hashes so old evidence does not recreate a removed note.

After a completed turn, generation waits for 60 seconds without foreground work and runs at most once per project every 10 minutes. It uses the selected model with no tools, at most 4,096 input tokens and 512 output tokens, a 30-second timeout, and no automatic cloud fallback. New foreground input cancels the auxiliary request. At most 1,024 estimated tokens of active notes are stored; new chats receive at most 512 tokens and 5% of their input budget, including recall framing. Failed, cancelled or stale-revision generation preserves the prior record. Exact auxiliary inputs, output settlement and usage are logged, and recall enters ordinary durable history as attributed historical data. Source file changes invalidate dependent generated facts; original session logs remain available.

## Usage license and release integrity

[RainyAgent source-available terms](LICENSE) permit personal and internal business use without a license fee, modification, and noncommercial redistribution; sale, paid hosting, and commercial redistribution require separate written permission. Startup and execution do not read device codes, activation codes or expiry dates, and settings contains no activation controls. Existing activation files remain in place and do not affect startup or execution. Projects, model settings and chats retain their existing storage locations.

The production carrier authenticates its resource inventory using a public release key embedded at build time and retains Electron ASAR integrity protection. Build keys are independent of user data: the default lives in the ignored build directory, or RAINY_RELEASE_SIGNING_KEY selects an existing Ed25519 private-key file; private keys never enter the distribution. Windows Authenticode signing uses a separately configured certificate.

## Known limitations and deferred work

The release target is Windows x64; signing status and platform/model acceptance belong to the exact artifact in [Validation](VALIDATION.md). Other WSL2 distributions and model endpoints need their own acceptance runs. The extension editor uses JSON and does not implement marketplace or OAuth workflows. Exact counting requires a tokenizer endpoint for the deployed model's whole request. Source retains upstream modules; the production graph is separately trimmed. No independent invariant entry is exported because this desktop application is verified through its composed profile and installer tests rather than a reusable plugin invariant contract.

The [release validation record](VALIDATION.md) owns measured browser performance and acceptance coverage. Local OCR, PDF rendering and BPE run in the browser; individual acceptance cases do not establish document fidelity for every input or long-running OCR stability.

The count of 38 describes tool-package content, not the number of tools that passed functional acceptance. Command-line and offline-web checks are recorded per tool and artifact; the previous release's acceptance total does not apply to this expanded catalog. Native third-party GUI behavior, first-run prompts and actual UAC consent interaction require separate acceptance. Clean-Windows installation and restart results are recorded per artifact in the final acceptance record. Headless directory evidence uses an explicit bridge adapter and covers the directory interface. Per-tool acceptance remains separate from directory, installer and environment tests; the final validation record must identify the tested artifact and remaining cases.
